# meridian-dev-workflow

Agent profiles and skills for the dev orchestration workflow.

## Releasing

Use `meridian mars version` for releases:

```bash
meridian mars version patch --push       # bump, commit, tag, push
meridian mars version minor --push       # minor bump when scope warrants it
```

This bumps `mars.toml`, rebuilds the committed `plugin/` tree and its marketplace catalogs (`.claude-plugin/`, `.cursor-plugin/`, `package.json`) at the new version, promotes CHANGELOG.md `[Unreleased]` to the new version, commits, tags, and optionally pushes. Never edit `plugin/` or the catalogs by hand; run `meridian mars build plugin` after changing a source file if you want the tree current before a release. Write changelog entries under `[Unreleased]` as you work — `meridian mars version` handles the rest.

**Meridian session roots:** Meridian spawns resolve `MERIDIAN_TASK_DIR` for the
checkout where source work happens, but `MERIDIAN_PROJECT_DIR` stays anchored to
the session control root for state, profiles, and context. Nested
`meridian ...` commands use project-root resolution, so CWD alone may not target
this package. For package releases, pass the package root explicitly:

```bash
meridian -C "$PWD" mars version patch --push
```

Use explicit `-C <package-root>` whenever running Meridian commands for this
package from an inherited Meridian environment. For task checkouts, prefer
`meridian -C "$MERIDIAN_TASK_DIR" ...`.

### After Release

Downstream repos pick up new versions via:
```bash
meridian mars add meridian-dev-workflow@vX.Y.Z
meridian mars sync
```

## Structure

```
agents/           # Agent profiles (.md with YAML frontmatter)
skills/           # Skill definitions (SKILL.md + resources/)
mars.toml         # Package manifest
mars.lock         # Generated local lock — ignored, do not track
.mars/            # Generated — do not edit directly
```

## Editing

Patch source files only:
- Agent definitions: edit `agents/*.md`
- Skills: edit `skills/*/SKILL.md` and their source resources

Never patch generated copies. In particular, do not edit `.mars/` directly —
it is generated by `meridian mars sync` and manual changes there will be
overwritten. If a generated `.mars/` file looks wrong, fix the corresponding
source file instead, then regenerate/sync.

After editing, test locally by running `meridian mars sync` in a downstream repo that imports this package.

## Watching

Behavior a released change expects but no real run has shown yet. Check it on
the next runs that exercise it, then delete the entry, fixing the prompt first
if the runs show otherwise.

- **Leads run the lifecycle from `/dev-workflow`, not their bodies.** On the
  next tech-lead and solo-dev runs: a returning spawn is not a stopping
  point; an unclear point is written to the work directory with the call
  made, and the questions come to the user at the end; a failing test is
  triaged before either side is changed; review lanes are staffed from
  `reviewers.md` and stop at its limits.
- **tech-lead with `/parallel-execution` loaded on every run.** A single
  change that doesn't split gets one lane, not a DAG.
- **tech-lead without `/dev-principles` loaded.** It still holds the
  structural bar when reading spawn output and plans (entanglement,
  deletion, enabling refactors first); if its judgments go soft, the skill
  goes back on `load:`.
- **coder, frontend-coder and investigator with `/llm-writing` available.**
  They load it before a commit message, changelog entry or report; if they
  never do, the description still isn't firing.
- **ux-lead's body overrides keep-going.** It still shows each change and
  waits for the human, and runs review and probe once per coherent change.
- **design-lead reaches its loop through `/architecture` and
  `reviewers.md`.** It enumerates edge cases before committing, offers built
  variants when uncertain, challenges the converged design with the three
  lanes, and brings the impasse to its caller at the round limit.
- **`/pre-dev` names the worktree as the task's default checkout (0.16.2),
  not "the work item's source checkout".** On the next tech-lead run that
  creates or reuses a worktree under Meridian: it still sets the work item's
  checkout (`meridian work task-dir`) so its spawns land in the worktree, and
  parallel lanes still get their own.
